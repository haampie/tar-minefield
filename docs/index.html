Tar file extraction test suite

This project provides an extensive test suite and documentation for tar file extraction, with the goal of ensuring that implementations extract tar archives the same way.

There are dozens of implementations of tar file extraction out there, from command line tools to libraries for programming languages. Because the tar file format leaves room for interpretation, different implementations can extract certain crafted tar files in different ways.

This is a security concern: for example, when a security scanner and the extractor use different tar implementations, the scanner could inspect other files than the ones that end up on disk.

By assigning identifiers to these ambiguities, and providing test cases and usage data, this project aims for tar implementations to converge on a strict parser and identical behavior.

This project proposes a default policy that rejects the vast majority of ambiguities in tar files that could make implementations extract different files, while ensuring that nearly every source tarball already published can still be extracted. Of the 82,587 source tarballs of Spack, nixpkgs, Guix and live-bootstrap, and samples of PyPI, crates.io and RubyGems, it accepts 99.75% (per ecosystem).

Comparison of different tar implementations¶

Click a case for its page.

Each case has a permanent identifier, such as F15, whose letter is its category:

  • F framing: which members an archive has.
  • N names: what path each member has.
  • K kinds: the mode of each member: file, directory, link or executable.
  • S order and state: how members combine into a directory tree.

A case's page shows its archive block by block, what every implementation makes of it, and how common it is in source tarballs.

Policy¶

This section defines a working draft of the default policy1, which accepts, tolerates or rejects each case below, based on data from the 82,587 distinct release tarballs of Spack, nixpkgs, Guix and live-bootstrap, and samples of PyPI, crates.io and RubyGems.

The prevalence column is an estimate of the likelihood of encountering a case in practice, from a scan of these tarballs.

1 A policy can be stricter and also reject the tolerated cases, at the cost of rejecting tarballs that are fairly common. That suits special-purpose tools, such as an extractor for a single ecosystem, where it can be checked against every tarball ever published there.

Contributing¶

Issues and pull requests are welcome on GitHub: a new case, an implementation for the comparison, or a tarball that the default policy gets wrong. A case that shows a vulnerability that is not yet disclosed is reported privately first: see SECURITY.md.
